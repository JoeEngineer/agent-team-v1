# 1.0.0 and 1.0.1 live runs

Seven live runs of the CI-wait harness (`tests/live/ci-wait-live.js`) on 2026-11-13, against the same scratch repo, fixed milestone and Director models as the 0.6.0 runs in [2026-11-12-ci-wait-live.md](2026-11-12-ci-wait-live.md): Claude `opus` and Codex `gpt-6.1-sol`. They were run to check the 1.0.0 guidance rewrite (decisions 0019 and 0020), which until then had only been checked against the rule inventory and unit tests.

**Result.** 1.0.0 had three wording regressions, each found by a run and fixed in 1.0.1. On the 1.0.1 head (`4329907`) both Directors completed the milestone. Claude passes all four harness targets. Codex passes three; the harness scores the fourth (CI turns per task PR) as FAIL, but every turn it counts beyond one per PR is a text mention of a script name, not a look at CI (see "The Codex per-PR count").

Each configuration was run once. These are single runs, not averages, and run-to-run variation is large (the Codex Director opened 3, 4 and 5 task PRs for the same milestone).

## The three regressions

### 1. A refused push of `STATUS.md` stopped the milestone (run 2)

The scratch repo's ruleset requires a status check on `milestone/*`, so GitHub refuses a direct push to the milestone branch. The Codex Director pushed `STATUS.md`, was refused, and stopped: "The plugin prohibits working around that refusal."

0.6.0 said not to work around the guard or a ruleset that refuses a **merge**. The rewrite condensed that to "when the guard or a branch rule refuses something". In 0.6.0 Directors sent the records through a PR (the cw9 runs each have one). The Claude Director in run 1 did not stop, but it never pushed the records at all, which is also wrong.

**Fix 1:** rule 9 covers guard blocks and refused merges again. Loop step 8 says what to do when the records push is refused: send them through a PR into the milestone branch, once before the milestone PR. Runs 3, 4, 6 and 7 all did that.

### 2. The Codex Director read CI itself (run 4)

On the first task PR, while its reviewers were still waiting, the Director ran `gh pr checks 92` and read the repo's auto-merge setting and the branch rules. On the records PR it ran `gh pr checks 93` before merging. That is two real CI turns beyond one per PR.

0.6.0 said "The reviewer waits for CI, not you" and not to re-check CI the reviewer had reported. The rewrite dropped the sentence as implied by "merge only with `merge-task.js`". It was not implied strongly enough for this Director.

**Fix 2:** rule 5 says CI is the reviewer's wait and the script's gate, not the Director's, and that the first merge's `--names` prints the check names. In runs 5 and 7 the Codex Director ran no `gh pr checks` and used `--names` on its first merge.

### 3. One failed guard lookup stopped the milestone (run 5)

After two clean merges, the guard's base-branch lookup for the third `merge-task.js` call failed in 0.6 seconds and the guard blocked it: "could not confirm the base branch of PR 106 — refusing to merge blind. This needs the user." The Director stopped, with one reviewed, green PR unmerged. The transcript doesn't show why the lookup failed; the same lookup had worked twice in the previous two minutes, so a network error is the likely cause.

This path is not new: the guard does the same lookup for a typed `gh pr merge`, and would have blocked the same way in 0.6.0. It did not happen in the six 0.6.0 runs.

**Fix 3:** the guard still blocks (fail closed). Its message now names the check to run and says that running the same command again once is not a way around the guard; if it still can't be confirmed, it needs the user. Rule 9 tells the Director to do what the guard's message says. **This fix has unit tests but was not exercised live**: no lookup failed in runs 6 and 7.

## The Codex per-PR count

The harness scores run 7 as FAIL: "#128: 2, #124: 1, #123: 1, #122: 3, #121: 2; 2 unattributed CI reads ... (11 for 5 task PRs)". I went through all 14 turns it counted:

| Turns | What the command was | A look at CI? |
|---|---|---|
| 5 | `merge-task.js <n> …`, one for each task PR | Yes: the one allowed per PR |
| 1 | `archive-logs.js …; ci-wait.js 127 --once` on the milestone PR | Yes: the close check |
| 5 | `log-event.js delegation` with a reviewer task card piped in from a PowerShell here-string. The card's CONTEXT line names `ci-wait.js <n>` | No |
| 2 | A reviewer task card built in a JavaScript string in the same call as a `git pull` or a STATUS edit | No |
| 1 | A `STATUS.md` edit that appends the sentence "merged by merge-task.js" | No |

So the Director made one CI turn per task PR and one on the milestone PR. The other eight are the parser reading script names inside data. The parser keeps a PowerShell here-string when it is piped to an interpreter, which is right for `| node` running code and wrong for `| node log-event.js`, where the text is JSON. Run 4 has one such miscount as well; its other two extra turns were real (regression 2).

I did not change the parser. Its rules were settled over several review rounds in the ci-wait milestone, and a change that hides text mentions could also hide a real CI look. It needs its own task: drop here-string and heredoc bodies piped into `log-event.js`, and don't count a script name inside a quoted string appended to a file.

## What this does and doesn't show

- **Shows:** on the fixed milestone, with 1.0.1, both Directors finish, merge only through `merge-task.js`, don't watch or poll CI, report complete only after the checks finish, and send the records through a PR when a direct push is refused.
- **Doesn't show:**
  - Anything about compaction. These runs are too short to compact, so the post-compaction note and the "re-read the reference" rule were not exercised.
  - The `queued` and `waiting` paths of `merge-task.js`. Every merge found CI green, because the reviewer had waited.
  - GitLab.
  - Fix 3 in a live run.
  - Whether the shorter reviewer, implementer and coach files changed review quality. Review `ci` values were all green and no review was `pending`; findings were not compared.
